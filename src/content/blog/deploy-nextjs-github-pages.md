Deploying a Next.js application to GitHub Pages is one of the most cost-effective ways to get your project live on the internet. GitHub Pages provides free static hosting with custom domain support, HTTPS certificates, and global CDN delivery — all at no cost. While Next.js is traditionally associated with Vercel, its static export feature makes it fully compatible with any static hosting platform, including GitHub Pages.

This guide walks you through the entire process from scratch: configuring Next.js for static export, setting up GitHub Actions for automatic deployments, handling the base path for project pages, and troubleshooting the most common issues. Whether you are deploying a portfolio, a blog, or a documentation site, you will have your Next.js app live on GitHub Pages by the end of this tutorial.

## Prerequisites

Before you begin, make sure you have the following set up:

- **Node.js 18+** installed on your machine
- A **GitHub account** with a repository created for your project
- Basic familiarity with **Git** commands (push, commit)
- A Next.js project (version 13 or 14 with App Router, or version 12+ with Pages Router)

If you do not have a Next.js project yet, create one quickly:

```bash
npx create-next-app@latest my-app
cd my-app
```

## Step 1: Configure Next.js for Static Export

GitHub Pages serves static files only — it does not run a Node.js server. This means you need to configure Next.js to generate a fully static build. Open your `next.config.js` (or `next.config.mjs`) and add the `output: 'export'` configuration:

```javascript
/** @type {import('next').NextConfig} */
const nextConfig = {
  // Generate a fully static build (no server-side rendering)
  output: 'export',

  // Optional: Disable image optimization for static export
  // Static export does not support Next.js Image Optimization
  images: {
    unoptimized: true,
  },
};

export default nextConfig;
```

The `output: 'export'` flag tells Next.js to output static HTML, CSS, and JavaScript files to the `out/` directory during the build process. This directory is what GitHub Pages will serve.

**Important:** When using `output: 'export'`, the following Next.js features are **not supported** because they require a server:

- API Routes (`app/api/` or `pages/api/`)
- Server-side Rendering (SSR)
- Incremental Static Regeneration (ISR)
- Middleware
- Image Optimization (use `unoptimized: true` as shown above)

If your project uses any of these features, you have two options: refactor to remove the dependency on server-side features, or use a platform that supports Next.js server-side rendering like Vercel or Netlify.

## Step 2: Set the Base Path for Project Pages

GitHub Pages hosts sites at one of two URLs:

- **User/Organization page:** `https://username.github.io/`
- **Project page:** `https://username.github.io/repo-name/`

If you are deploying to a user page, you can skip this step. But if you are deploying to a project page, you must set the `basePath` so that Next.js generates correct asset URLs:

```javascript
const nextConfig = {
  output: 'export',
  images: {
    unoptimized: true,
  },

  // Set this to "/repo-name" for project pages
  // Remove this line entirely for user/org pages
  basePath: '/my-repo-name',

  // Ensure trailing slashes for clean GitHub Pages URLs
  trailingSlash: true,
};
```

The `basePath` prefix is automatically applied to all links, static assets, and API routes generated by Next.js. The `trailingSlash: true` setting ensures that GitHub Pages correctly resolves your routes, since it does not support clean URL rewrites.

## Step 3: Create the GitHub Actions Workflow

GitHub Actions can automatically build and deploy your Next.js site every time you push to the `main` branch. Create the workflow file at `.github/workflows/deploy.yml`:

```yaml
name: Deploy to GitHub Pages

on:
  push:
    branches: ['main']
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: 'pages'
  cancel-in-progress: true

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      - name: Build
        run: npm run build

      - name: Upload artifact
        uses: actions/upload-pages-artifact@v3
        with:
          path: ./out

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - name: Deploy to GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v4
```

This workflow does the following: checks out your code, sets up Node.js, installs dependencies, runs `npm run build` (which outputs to `out/`), uploads the artifact, and deploys it to GitHub Pages. Every push to `main` triggers a fresh build and deploy.

## Step 4: Enable GitHub Pages in Your Repository

With the workflow file in place, you need to enable GitHub Pages in your repository settings:

1. Go to your repository on GitHub
2. Navigate to **Settings > Pages**
3. Under "Source," select **GitHub Actions** (not "Deploy from a branch")
4. Click **Save**

This tells GitHub Pages to use the artifact produced by your GitHub Actions workflow rather than serving files directly from a branch.

## Step 5: Push and Deploy

Commit all your changes and push to the `main` branch:

```bash
git add .
git commit -m "Configure Next.js for GitHub Pages deployment"
git push origin main
```

Go to the **Actions** tab in your GitHub repository to watch the build and deploy progress. Within 1-2 minutes, your site will be live at `https://username.github.io/repo-name/`.

## Handling Custom Domains

If you want to use a custom domain (e.g., `myapp.com`) instead of the default `github.io` URL:

1. In your repository, go to **Settings > Pages > Custom domain**
2. Enter your domain name and click **Save**
3. In your DNS provider, create a `CNAME` record pointing to `username.github.io`
4. Wait for DNS propagation (up to 48 hours, usually much faster)

GitHub automatically provisions and renews SSL certificates for custom domains, so you get HTTPS for free.

## Common Issues and Fixes

### 404 Errors on Page Refresh

If navigating to a page works but refreshing gives a 404, ensure `trailingSlash: true` is set in your `next.config.js`. GitHub Pages does not support URL rewriting, so it needs the trailing slash to find the `index.html` file inside each directory.

### Blank Page or CSS/JS 404s

If your page loads but all styles and scripts are 404, your `basePath` is likely misconfigured. Verify that it exactly matches your repository name, including the leading slash: `/my-repo-name`.

### Build Fails with "Export encountered errors"

This usually means you are using server-side features (API routes, `getServerSideProps`, etc.) in a static export. Review your pages and components for any server-only code and either remove it or switch to `getStaticProps` / client-side data fetching.

## Alternative: Use Vercel for Zero-Config Deployment

If you want to skip the manual configuration entirely, deploying Next.js to Vercel is the simplest path. Vercel is built by the creators of Next.js and supports all its features including SSR, ISR, and Edge Functions. Simply connect your GitHub repository to Vercel, and every push triggers an automatic deploy with zero configuration needed.

## Conclusion

Deploying Next.js to GitHub Pages is straightforward once you understand the static export configuration. The combination of `output: 'export'`, correct `basePath` setting, and GitHub Actions gives you a fully automated deployment pipeline for free. For portfolio sites, blogs, and documentation, this setup provides everything you need with no hosting costs.

For more complex applications that require server-side rendering, consider Vercel or Netlify, which provide first-class Next.js support with additional features like serverless functions and edge middleware. But for static sites, GitHub Pages remains an excellent, zero-cost option.
